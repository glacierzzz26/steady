## 0. 最重要的前提：系统里没有一分真钱

你看到的"自动买入"，**不是真的去买股票**。

这套系统是一个 **模拟交易（纸面交易 / 模拟盘）** 平台：

- 后端在**数据库里**模拟撮合成交：下单、成交、持仓、扣手续费、算盈亏，全在内存账本 + PostgreSQL 里完成。
- **不连接任何券商**（QMT / CTP / 同花顺 都不接），没有真实资金进出。
- 真实现单是 **Phase 3（未来阶段）**，目前代码里只是预留了方向，没有任何券商接口实现。

证据就在代码注释里：`backend/internal/service/broker.go:55`

```go
// Broker 模拟券商成交（纯函数，不持有状态）
```

整个项目对外部世界的真实调用只有三类（全都不是券商）：
1. **BaoStock / AkShare** 拉行情数据（collector 用；阶段 3 起 Tushare 已移除）
2. **飞书 webhook** 推通知
3. **云端 LLM API** 做简报解读

所以你现在看到的所有"买入 / 卖出 / 持仓 / 净值"，都是数据库里的数字游戏，目的是**验证策略是否有效**，不是替你赚钱。真正的意义是：等策略在模拟盘上跑稳了、回测可信了，再接券商实盘。

## 1. 项目是什么

**一句话**：个人 A 股量化研究与模拟交易平台，从"拉数据"到"算策略"到"模拟交易"到"看收益"的完整闭环。

**设计原则**（README.md）：
1. 数据可靠 > 策略复杂
2. 可解释策略 > 黑盒模型
3. 模拟验证 > 实盘尝试
4. 长期复利 > 短期暴利

**五个服务**，单机 docker-compose 部署（不上 k8s）：

| 服务 | 语言 | 干什么 |
|---|---|---|
| `collector` | Python | 从数据源采集行情/财务/估值/日历，写入数据库 |
| `quant-engine` | Python | 算因子 → 算信号 → 组装早报 → 跑回测 → 推飞书通知 |
| `backend` | Go | REST API + **模拟交易**（下单/持仓/净值/对账）+ LLM + 每日调度 |
| `frontend` | React+TS | 网页 Dashboard，看数据看持仓看回测 |
| `postgres` / `nginx` | — | 数据库 / 唯一对外入口（:80） |

**服务之间怎么通信**：服务之间**不互相调 HTTP**，数据库（PostgreSQL `quant_system`）是唯一通信中枢——collector 写数据，quant-engine 读数据算信号，backend 读信号做模拟交易，quant-engine 再把结果推给飞书。所有容器绑定 127.0.0.1，只有 nginx 暴露 80 端口，API 无鉴权靠"内网 + 单入口"兜底。

架构图：

```
  A股数据源 (Tushare 主源 + AkShare 兜底)
        │
        ▼
┌──────────────┐   写     ┌─────────────────────────┐

└──────────────┘          │ 账户/持仓/委托/成交/净值   │
        ▲                 └─────────┬────────────────┘
        │                           │ 读

        │                   │ quant-engine   │──▶│ 飞书机器人 │
        │                   │ 因子/信号/回测/早报│   └──────────┘
        │                   └───────┬────────┘
        │                           │ 读信号
```

## 2. 一条主线看懂数据流

整个系统每天做一件事：**选 20 只股票模拟买入，跑不动的卖掉**。数据沿着这条线流：

```
Tushare/AkShare 原始数据
        ↓  collector 采集、清洗
  行情/估值/财务/日历 表
        ↓  quant-engine 19:00 算因子
   factor_value（每只股票 6 个因子值 + 横截面归一化）
        ↓  quant-engine 19:30 算信号
   strategy_signal（每只股票一个动作：BUY / SELL / HOLD + 综合分）
        ↓  backend 19:35 模拟交易
   order / trade / position / account（下单、成交、持仓、账户资金）
        ↓  backend 21:05 / 21:15
   account_nav（净值曲线） + 对账校验
        ↓
   前端展示 / 飞书推送
```

下面逐环节拆解。

## 3. 因子：策略的"打分依据"

### 3.1 什么是因子

因子就是**给股票打分的单项指标**。每只股票每天算出 6 个因子的值，然后综合成一个 0~100 的总分，总分越高排名越靠前，越可能被买入。

> 因子计算代码：`quant-engine/app/factor_service.py`
> 因子的公式实现：`quant-engine/app/factors/`（trend.py / value.py / financial.py）

### 3.2 六个因子清单

| 因子 | 类别 | 方向 | 含义 | 公式 / 逻辑 |
|---|---|---|---|---|
| `ma_trend` | 趋势 | 越高越好 | 均线趋势 | MA5 > MA20 为 1，否则 0（`factors/trend.py:10-17`） |
| `macd_signal` | 趋势 | 越高越好 | MACD 金叉/死叉 | DIF > DEA 为 1，否则 0（`factors/trend.py:20-26`） |
| `pe_ratio` | 价值 | 越低越好 | 市盈率 | 当日 PE_TTM；亏损（PE≤0）取不到（`factors/value.py:24-27`） |
| `pb_ratio` | 价值 | 越低越好 | 市净率 | 当日 PB；PB≤0 取不到（`factors/value.py:30-33`） |
| `roe_quality` | 质量 | 越高越好 | ROE 净资产收益率 | 最新一期已公告的 ROE（`factors/financial.py:26-28`） |
| `debt_risk` | 风险 | 越低越好 | 资产负债率 | 最新一期已公告的资产负债率（`factors/financial.py:31-33`） |

**每个因子的权重**（存在 `factor_definition` 表里，`deploy/postgres/init.sql:265-272`）：

```
ma_trend 0.20 + macd_signal 0.20 = 趋势 40%
pe_ratio 0.15 + pb_ratio 0.15   = 价值 30%
roe_quality 0.20                = 质量 20%
debt_risk 0.10                  = 风险 10%
```

你看，**六因子权重相加正好就是策略描述里说的"趋势40%+价值30%+质量20%+风险10%"**。策略表里的类别权重（`strategy.factor_weights`）只是给人看的汇总，真正参与打分的是这张逐因子权重表。

### 3.3 为什么单看因子值没用，要做"横截面归一化"

6 个因子量纲完全不同：MA5>MA20 只有 0 或 1，PE 可以是 5 也可以 500，ROE 是百分比。没法直接比较。

所以每只股票的每个因子，都要和**当天全市场（沪深300+中证500，约 800 只）**一起做横截面处理（`factor_service.py:normalize_cross_section`，`133-152` 行）：

```
原始值 → winsorize 截断（1%/99% 分位，去掉极端值）
       → 百分位排名 rank（在当天全市场里排第几）
       → 按方向翻正（desc 因子取反，让"越低越好"变成"排名越前分越高"）
       → 得到 0~1 的 normalized 值
```

结果写进 `factor_value` 表：每天每只股票每因子一行，存 `value`（原始值）、`rank`（横截面名次）、`normalized`（0~1 归一值）。

### 3.4 综合评分

```
综合分 score = 100 × Σ(每个因子权重 × normalized)
```

（`factor_service.py:score_cross_section`，`155-173` 行）得分 0~100，越高越好。

**注意**：只有 6 个因子全取得到的股票才参与评分和排名（缺任何一个就剔除，比如 ST、停牌、刚上市没有财务数据的）。这保证了排名的公平性。

### 3.5 防未来函数（用了真实交易时看不到的未来的数据 = 作弊）

这一点是这个项目做得比较严谨的地方。因子计算刻意做了三个"as-of"处理（只准用那个时间点之前**已经公开**的信息）：

1. **财务因子**：只用 `announce_date <= trade_date` 的记录（公告日 ≤ 交易日）。财报是滞后披露的，Q1 的财报可能 4 月底才公告，那就不能拿 3 月底的模拟去用它。（`factor_service.py` 财务输入）
2. **估值因子**：取"as-of 30 日回看窗口"，取最近一日有估值的那天（停牌日就取前一交易日），避免未来数据混入。（`factor_service.py:47-111`）
3. **行情因子**：用**前复权价**计算，`close × adj_factor / 窗口最新 adj_factor`，分红除权后价格才不会假性跳变。（`factor_service.py:52-67`）

> 但也存在一个**已知的 look-ahead 风险点**：行情类因子（MA/MACD）是"当日收盘后算出信号、当日就以收盘价模拟成交"，等于当天就知道当天收盘价——这在模拟盘里合法，但真实盘中不可能收盘价一出来就成交。优化路线图里把它列为最高优先的校准项（见 §9.7）。

## 4. 策略：怎么从 800 只里选 20 只

### 4.1 唯一的真实策略：multi_factor（多因子轮动）

**重要事实：整个项目只实现了一个策略 `multi_factor`。** 文档里还规划了动量策略 `momentum.py`，但那个文件没有实现（只是一个占位/未完成文件）。当前系统 100% 由多因子轮动这一个策略驱动。

策略代码：`quant-engine/app/strategies/multi_factor.py`（核心逻辑在 `44` 行后的 `MultiFactorStrategy`）

### 4.2 策略怎么选股：轮动规则

每天收盘后，对全市场股票按综合分排名，然后套用一条很朴素的规则（`multi_factor.py:31-41` 的 `rotation_action`）：

| 状态 | 条件 | 动作 |
|---|---|---|
| 未持仓 | 排名 ≤ 15（buy_buffer） | **BUY** 买入 |
| 已持仓 | 排名 > 30（sell_buffer） | **SELL** 卖出 |
| 其余 | — | **HOLD** 持有不动 |

参数都配置在 `strategy.params` 里（`init.sql:283-286`）：

```
universe: hs300+zz500   # 股票池：沪深300 + 中证500，约 800 只
top_n: 20               # 目标持仓数：想持有 20 只
buy_buffer: 15          # 排名 ≤15 才买
sell_buffer: 30         # 排名 >30 才卖
max_position_pct: 0.20  # 单只股票仓位上限 20%
```

**为什么要"缓冲带"（15 和 30 之间留空）？**
如果排名一变就买卖，每天都会大换手，手续费和滑点会吃光收益。所以设计成：只有掉到 30 名开外才卖、只有冲进前 15 才买——中间这段（16~30 名）即使排名波动也拿住不动，**减少无效换手**。这是经典的"轮动 + 缓冲"思路。

**一个具体例子**，帮你看懂整条链路：

```
某交易日收盘后：
① 19:00  quant-engine 算出 800 只股票的综合分（0~100）
② 排名：股票 A 排第 8 名，股票 B 排第 22 名，股票 C 排第 35 名
③ 假设当前没持有 A：A 排第 8（≤15）→ 信号 BUY
   B 排第 22（16~30 之间）→ 不管持不持有都是 HOLD
   C 排第 35：若持有 → 信号 SELL；若没持有 → HOLD
④ 19:30  生成 strategy_signal，写进数据库
⑤ 19:35  backend 读取信号，对 A 模拟买入、对 C 模拟卖出
```

### 4.3 信号长什么样

`strategy_signal` 表每天约 800 行，每只股票一行：

```
strategy_name | code | trade_date | score | action | reason
multi_factor  | 600519 | 2026-08-21 | 87.3 | BUY   | 未持仓且排名8≤15
multi_factor  | 000001 | 2026-08-21 | 45.1 | HOLD  | 排名22在缓冲带内
multi_factor  | ...   | ...        | ...  | ...   | ...
```

> 一个实现细节（对理解持仓有帮助）：策略判断"是否已持有"时，**不是去读 position 表，而是从最近一次历史信号重建**——昨天 action ∈ {BUY, HOLD} 的股票视作今天持有，昨天 SELL 的视作已清仓（`multi_factor.py` 开头 docstring + `prepare()`）。这与后端真正的持仓表在"信号日"这个时点上是一致的，但注意它是信号层的简化模型。

## 5. "自动买入"到底怎么发生的（你最关心的部分）

### 5.1 时间点

```
19:30  quant-engine 生成当日信号（写 strategy_signal）
19:35  backend 定时任务触发"自动交易"（ExecuteDay）
```

backend 的调度注册在 `backend/cmd/server/main.go:71-83`，自动交易由内部 30 秒 ticker 的调度器触发（`internal/service/scheduler.go`），并带"重启补跑"语义——如果 19:35 时进程刚好不在线，重启后检测到当日还没执行，会补跑一次（`scheduler.go:66-78, 113-142`）。

### 5.2 ExecuteDay：单事务完成全流程

核心函数 `backend/internal/service/trading.go:171` `ExecuteDay`。它在**一个数据库事务**里完成（所以要么全成功要么全回滚，不会出现"买了但没记账"）：

```
1. 锁定模拟账户行（防止并发）
2. 幂等检查：当日净值快照已存在 → 直接跳过（说明今天跑过了）
3. 用账户现金初始化一个内存账本 Ledger（trading.go:46，纯内存，镜像 Python 端 Portfolio）
4. 执行策略信号：
   a. 先卖后买（先释放现金，再用现金买）
   b. 遍历信号，按规则撮合（见下节）
5. 把成交结果写回数据库：
   委托单 order、成交 trade、持仓 position、账户 account
```

### 5.3 撮合规则：完全照搬 A 股真实规则

模拟撮合不是随便记个账，而是尽可能还原 A 股交易约束（`backend/internal/service/broker.go`，回测侧镜像在 `quant-engine/app/backtest/broker.py`）：

| 规则 | 说明 |
|---|---|
| **成交价** | 当日收盘价 ± 0.1% 滑点（买入 +0.1%，卖出 −0.1%） |
| **整手** | 买入必须是 100 股的整数倍（不足 100 股的不买） |
| **T+1** | 当天买的当天不能卖（`available_qty` 冻结，次日才解冻；`Ledger.UnfreezeT1` trading.go:97） |
| **涨跌停拦截** | 涨停（+10%）的股票拒绝买入、跌停（−10%）的拒绝卖出，记拒单（分板块：主板 10% / 创业板科创 20% / 北交所 30% / ST 5%） |
| **手续费** | 佣金万 2.5、最低 5 元；印花税万 5、仅卖出时收 |
| **现金不足** | 买不起 100 股就逐档减 100 股重试，减到 100 股还买不起则放弃 |

### 5.4 为什么说它"不会真买"

回到开头：`broker.go:55` 的注释白纸黑字写着 `// Broker 模拟券商成交（纯函数，不持有状态）`。全代码库搜不到任何券商 API 调用。它的成交就是把"想买 100 股、按收盘价×1.001 成交、扣佣金"这笔账记进数据库。**资金在表里进出，钱在账户表里增减，仅此而已。**

### 5.5 幂等：重复跑不会重复买

如果 19:35 的自动交易被手动再触发一次，会发生什么？`ExecuteDay` 第一步就检查：**当日净值快照（account_nav）已存在 → 直接跳过**。所以同一个交易日重复执行是安全的，不会把 20 只股票买两遍。

### 5.6 前端那个"手动执行"按钮

前端交易页有个"手动执行"按钮（`frontend/src/pages/Trade/index.tsx:131-149`），它 POST `/api/v1/trading/execute-day`，触发的是 `ExecuteDayManual`（`backend/internal/service/execute.go:56-89`）= 跑一遍同一套模拟撮合 + 补一个净值快照。

**注意**：它不是"手动下单真去买"，只是**手动触发当天本来就该自动跑的模拟撮合**（比如当天自动任务没跑成，用它兜底补跑）。前端虽然有下单表单（API 里有 order 接口），但**下单表单并没有真正接到后端**——目前没有真实下单入口，这也符合"模拟盘"定位。

### 5.7 收盘后还有两步：净值快照 + 对账

```
21:05  净值快照：算当日账户净值、日收益、回撤，写 account_nav（幂等，重复跑不覆盖）
21:15  一致性对账：7 项独立复算（现金+市值=总资产、委托=成交、T+1 可卖数、幂等等），
        有偏差就推飞书告警
```

（`main.go:71-83` 注册；`internal/service/consistency.go` 对账逻辑）这两步保证"账是平的"——模拟盘的钱不会凭空多出来或消失。

## 6. 一天的完整时间线

把三个服务的定时任务合并起来看，一个交易日是这样转的：

| 时间 | 谁 | 干什么 |
|---|---|---|
| 08:45 | collector | 采集市场热点（隔夜外盘/板块/资金流/涨停池）→ `market_hotspot` |
| 09:00 | collector | 更新股票列表（Tushare stock_basic → AkShare 兜底）→ `stock_basic` |
| 09:05 | collector | 更新交易日历（近 2 年 + 未来 1 年）→ `trade_calendar` |
| 09:10 | quant-engine | 组装**早盘简报**（基于昨日数据）→ `morning_brief` |
| 09:15 | quant-engine | 飞书推送早盘简报 |
| 09:20 | backend | LLM 解读当日简报 → 飞书卡片 |
| 16:15 | collector | 同步指数行情（沪深300/中证500）|
| 16:30 | collector | 同步全市场日线行情（Tushare 快照 2 次调用，失败逐只降级 AkShare）→ `daily_price` |
| 16:45 | collector | 同步全市场估值（PE/PB/市值）→ `daily_valuation` |
| 18:00 | collector | 同步财务指标（最近 4 个报告期增量）→ `financial_indicator` |
| 18:05 | collector | 夜间回填（补历史日线到 2016-08-01 + 补估值滞后股）|
| 18:30 | quant-engine | 数据健康检查（7 项：覆盖率/缺失日/重复/价格异常/估值滞后/财务新鲜度/指数基准）→ `task_run` |
| 18:35 | quant-engine | 数据质量结果推飞书 |
| **19:00** | **quant-engine** | **计算因子**（6 因子 + 横截面归一）→ `factor_value` |
| **19:30** | **quant-engine** | **生成策略信号**（综合分排名 + 轮动规则）→ `strategy_signal`，推飞书 |
| **19:35** | **backend** | **自动模拟交易** ExecuteDay（买/卖/拒单）→ 飞书结果卡片 |
| 21:00 | quant-engine | 推送每日汇总报告 |
| 21:05 | backend | 净值快照 → `account_nav` |
| 21:15 | backend | 一致性对账 → 通过/告警飞书卡片 |
| 每 5 分钟 | quant-engine | 消费回测任务队列（有就执行）|
| 每 1 分钟 | quant-engine | 通知调度 tick（判到点推送 + "该做没做"监控）|

> 非交易日会怎样？collector 的夜间回填有交易日门控（`is_open != 1` 跳过），后端自动交易读不到当日信号自然不动作。周六日系统基本静默。

## 7. 周边能力：飞书通知 + LLM

### 7.1 飞书通知

**配置全部存在 `app_config.feishu.*` 表里**（页面「设置」可改，不读环境变量）。通知分两类：

1. **定时推送**：信号 / 自动交易结果 / 净值 / 日报 / 数据质量 / 早报，触发时间由 `notify_config` 表配置。
2. **事件推送**：回测完成、任务失败告警、手动触发。

**"该做没做"监控**（这个设计很有意思）：每 1 分钟的通知 tick 会查 `task_run` 台账，如果某个定时任务**到点没执行**（比如 19:00 因子没跑），宽限 30 分钟后推一条**红色"任务未执行"告警**。当日有任务失败的也会推红色告警。

> ⚠️ 当前代码只实现了**「@所有人」开关**（`feishu.at_all`），没有按 open_id @ 指定用户的功能。如果你之前记得"可以 @ 人"，那可能是规划，目前代码里没有。

### 7.2 LLM（AI 助手）

- **三大能力**：术语解释（≤200 字）、项目问答（基于静态知识库）、简报解读。
- **知识库是静态 markdown 文件**：`docs/llm/术语表.md` + `docs/llm/项目知识.md`，发布时只读挂载进 backend 容器。**LLM 绝不直连数据库**，唯一数据入口是白名单只读接口 `BriefReader`——这是个刻意设的硬约束，防止大模型被注入或读取敏感数据。
- 支持 openai / deepseek / qwen / glm 四种 provider，配置在页面设置里。

### 7.3 任务台账 task_run

这是整个系统的"监控中枢"表：**每个定时任务每天一行**，记录 success / skipped / failed 和详情。飞书告警、数据健康、前端"任务执行记录"页全读这张表。

## 9. 重要：设计文档 vs 实际实现（差异清单）

读代码时发现文档和实际有这些出入，值得知道：

| # | 差异 | 说明 |
|---|---|---|
| 1 | **动量策略未实现** | 文档规划的 `momentum.py` 策略不存在于实际运行，系统只有 `multi_factor` 一个策略 |
| 2 | **前端下单表单未接线** | 交易页没有真正的"手动下单"通路，唯一按钮是"手动执行"（触发模拟撮合）|
| 3 | **类别权重只是展示** | "趋势40%价值30%质量20%风险10%"是给人看的汇总，真正打分权重是 `factor_definition` 逐因子权重（两者数值恰好一致）|
| 4 | **持仓来源是重建的** | 策略判断"是否已持有"从历史信号重建，不是读 position 表（信号层与交易层在收盘后时点一致，但模型不同）|
| 5 | **Tushare 已实现但文档标 🚧** | `docs/优化路线图.md` 把"Tushare 主源"列为待办，但代码（8fb3fa9）早已实现 Tushare 主源 + AkShare 兜底，文档过期 |
| 6 | **财务表 pe/pb 是死列** | `financial_indicator` 表 DDL 里有 pe/pb 列但从不写入，PE/PB 实际走 `daily_valuation` 表 |
| 7 | **回测有 look-ahead 风险** | 信号当日生成、当日以收盘价成交，优化路线图列为最高优先校准项（待 T+1 成交对比验证）|
| 8 | **quant-engine 无重启补跑** | collector 和 backend 都有"重启补跑"，但 quant-engine 的 19:00 因子 / 19:30 信号若当时进程不在线**不会自动补跑**，只能靠手动 CLI 或等它暴露为"未执行"告警 |
| 9 | **Redis 未启用** | `backend/configs/config.yaml` 里注释预留，V1 不用，Phase 2 才引入 |
| 10 | **@ 指定用户未实现** | 飞书只有 @all 开关，无 open_id @ 特定用户功能 |

## 10. 常用操作（命令行）

手动补跑/重算（`quant-engine` 里）：

```bash
# 手动算某个交易日的因子
cd quant-engine && python -m app.cli factors --date 2026-08-21

# 手动生成信号
cd quant-engine && python -m app.cli signals --date 2026-08-21

# 手动触发模拟交易（等价于前端"手动执行"按钮）
curl -X POST http://127.0.0.1:8080/api/v1/trading/execute-day
```

数据回填（`collector` 里）：

```bash
# 回补日线（到 2016-08-01）+ 财务（20 个季度）
cd collector && python -m app.cli backfill

# 补估值滞后股票
cd collector && python -m app.cli backfill-valuation
```

生产发布（只在 master 分支）：

```bash
scripts/build-release.sh   # 产出 deploy/release/steady-<日期>-<SHA>/ 三件套
# scp 到 VM → cd 进去 → ./install.sh（幂等，自动复用数据卷和数据库密码）
```
