# 策略与风控（Iteration 4 · G11 策略生命周期 + 风控落执行层）

> 第二阶段研究闭环：把「策略」从库里的单例升级为**可管理的对象**——多策略并存、状态流转、前端配权、A/B 对比、风控参数落执行层。
> 状态：📋 定稿（2026-08-23）· 用户确认后登记 `design/README.md` 并按此执行。
> 关联：[接口契约 G11](./frontend-v2-api-contract.md#54-第四阶段24-策略生命周期--风控) · [优化路线图 优先级四](../../优化路线图.md) · [进度总表](../../进度总表.md)

## 1. 背景与目标

策略系统现状是「库里一条 `multi_factor`、权重全局在 `factor_definition`、前端 StrategyFactory 全 mock」。本迭代把它升级为研究闭环的**策略生命周期**：

1. **多策略并存 + 状态流转**：策略从单例 → 可 CRUD 的多版本对象，状态机 `draft → backtest → sample → active → paused/archived`，仅一个 `active` 驱动每日信号。
2. **权重/参数前端配置**：StrategyFactory 构建器接通真实 API——因子池勾选 + 滑杆配权 + 轮动/风控参数，保存进策略。
3. **多策略 A/B 对比**：回测支持按策略名跑，同一区间同假设并排对比，验证新策略再上线。
4. **风控参数落执行层**：`stop_loss`（个股止损）/ `drawdown_fuse`（组合回撤熔断）/ `industry_limit_pct`（行业集中度）在**实盘模拟盘与回测引擎**同口径生效；`max_position_pct` 已生效保持。
5. **风险指标**：回测结果补 `turnover`（年换手）/ `cost`（交易成本占比），回测页与对比页展示。

> **关键架构决策**：评分权重从「全局 `factor_definition.weight`」切换为「**策略自带因子级权重**（`strategy.factor_weights`）」。这样每个策略可以有独立权重组合（构建器滑杆改的正是因子级权重），且排名/分项/回测三处同源。`factor_definition.weight` 降级为「新建策略的默认值来源 + 因子定义展示」。

### 现状痛点（本迭代要解决的）

- 想试新参数/新权重只能直接改库 `factor_definition`/`strategy`，改完影响生产策略，**无草稿/回测/上线链路**。
- 回测只能跑 multi_factor 一种，**无法并排对比两个候选**。
- 止损/熔断/行业集中度完全缺失，模拟盘只看轮动信号硬买硬卖。

## 3. 设计决策

### 3.1 策略生命周期（多策略 + 状态机）

**`strategy` 表扩展**（name 仍为唯一标识，每版本一条独立记录）：

```sql
zh_name     VARCHAR(50),                     -- 中文名（前端展示，如「多因子轮动」）
version     VARCHAR(20) DEFAULT 'v1.0',      -- 版本号（展示/排序）
status      VARCHAR(10) DEFAULT 'draft',     -- draft/backtest/sample/active/paused/archived
updated_at  TIMESTAMP DEFAULT NOW()
```

**状态机**（前端 sec-note 已描述）：

```
draft ──→ backtest ──→ sample ──→ active ──→ paused ──→ archived
  ↑ 可编辑/可回退       ↑ 回测通过        ↑ walk-forward 通过
  └────── 任意状态 → draft（编辑/回炉）  active ⇄ paused 可往返
```

约束（服务层强制）：
- **同一时间仅一个 `active`**：`switch` 到 active 时，先校验目标存在且非 archived，再事务内把旧 active 置为 `paused`、新策略置 `active`。
- 只有 `draft` 可改（PUT）；`paused` 可恢复 active；`archived` 冻结不可改不可激活。
- 非 draft 状态不允许编辑 `factor_weights`/`params`（需要新版本再改）。

**版本化（fork）**：`POST /strategies/:name/versions` 复制当前策略为 `draft`，自动生成新 name（`multi_factor` → `multi_factor_v2`，去重则 `_v3`），`version` 递增，返回新 name。前端 mock 的 `mf_v2` 就是这种。

**信号生成/实盘读 active 策略**（去掉硬编码）：
- `tasks.generate_signals`：`select * from strategy where status='active'`，config 用该行 params，评分权重用该行 `factor_weights`；`strategy_signal.strategy_name` 用该策略 name。
- `trading.go execStrategy`：同样读 active 策略（含权重与风控参数）。
- 无 active 策略 → 跳过信号生成并记台账（数据诚实，不静默）。

### 3.2 权重口径切换（策略自带因子级权重）

**新口径**：`strategy.factor_weights` 存**因子级权重映射**（合计 1.0），例如：

```jsonc
{ "ma_trend": 0.2, "macd_signal": 0.2, "pe_ratio": 0.15,
  "pb_ratio": 0.15, "roe_quality": 0.2, "debt_risk": 0.1 }
```

**三处同步改为「策略权重」**（原来全走 `factor_definition`）：
1. `MultiFactorStrategy.calculate()`（实盘信号）：权重取策略行 `factor_weights`，缺失因子回退 `factor_definition`。
2. `ReplayStrategy`（回测）：`build_replay_strategy(db, top_n, strategy_name)` 读指定策略的 `factor_weights` + `params`。
3. Go `GetSignalRanks`/`GetSignalSubscores`（排名/分项）：先读 active 策略 `factor_weights`（Go map），对当日 `factor_value` 行在 Go 侧计算（替换原纯 SQL 的 `factor_definition.weight` 乘法）。

**迁移**：
- init.sql：`multi_factor` 种子 `factor_weights` 从 4 类改为 6 因子级映射（与 factor_definition 权重一致：0.2/0.2/0.15/0.15/0.2/0.1）。
- 部署库：`UPDATE strategy SET factor_weights = '<6因子映射>' WHERE name='multi_factor'`（老库只有一条）。

### 3.3 回测支持多策略 + A/B 对比

**`POST /backtests` 增加 `strategy_name`**（可选，默认 = active 策略；校验存在且非 archived）。`backtest_job.strategy_name` 已有列与唯一键，直接透传。

**Python 侧**：`create_job` / `build_replay_strategy` 增加 strategy_name 参数；`ReplayStrategy` 从该策略行加载 `params`（top_n/buffer/风控）与 `factor_weights`。

**A/B 对比接口** `GET /strategies/compare`：

```
GET /strategies/compare?base=multi_factor&candidate=multi_factor_v2
    &start=2019-01-01&end=2026-08-23&fill_mode=t1_open
```

- 校验两个策略都存在；同区间同假设各建一个回测 job（幂等复用已有结果），返回对比 DTO：

```jsonc
{ "base":   { "strategy_name":"multi_factor", "total_return":0.382, "annualized_return":0.051,
              "max_drawdown":-0.214, "sharpe":0.42, "turnover":8.6, "cost":0.012, "trades":120,
              "nav":[{ "date":"..","nav":.. }] },
  "candidate": { "strategy_name":"multi_factor_v2", "...": "同构" },
  "benchmark": { "code":"sh000300", "nav":[{ "date":"..","nav":.. }] } }
```

- 若任务未跑完（pending/running）→ 返回 `status`，前端轮询；failed → 返回 error。
- 同一 job 的配对运行（t_close/t1_open）沿用 Iteration 3 的 `_clone_strategy` 机制。

### 3.4 风控参数落执行层

**参数定义**（存于策略 `params`）：

```jsonc
{ "top_n": 20, "buy_buffer": 15, "sell_buffer": 30,
  "max_position_pct": 0.20,     // 单股仓位上限（已有，SizeBuyQty 生效）
  "stop_loss_pct": 0.15,        // 个股止损线：持仓亏损 ≥15% 强制卖出
  "drawdown_fuse_pct": 0.10,    // 组合回撤熔断：回撤 ≥10% 当日暂停新买入
  "industry_limit_pct": 0.30 }  // 单行业持仓市值占比上限（买前检查）
```

**实盘（Go `trading.go ExecuteDay`，每日固定顺序）**：

1. **止损扫描**（策略信号前）：遍历持仓，`profit_rate <= -stop_loss_pct` → 强制卖出当日可卖量，落 `strategy` 单（reason 前缀「止损」），计入 SellCount/Rejected 之外单独计 `risk_actions`。
2. **回撤熔断**：组合回撤 = `(total_asset − 历史峰值 total_asset) / 历史峰值`（历史峰值取 `account_nav` 中 trade_date ≤ 当日 的 MAX total_asset，含当日）。`drawdown ≥ drawdown_fuse_pct` → 当日**跳过全部策略 BUY**，SELL/止损照常；task_run 台账记录「熔断」。
3. **行业集中度**（BUY 撮合前）：目标股票 `stock_basic.industry`，加仓后该行业市值占比 > `industry_limit_pct` → 拒单（reason「行业集中超限」），计入 Rejected。
4. `max_position_pct` 继续由 `SizeBuyQty` 生效（不变）。

**回测（Python `engine.py`，镜像同口径）**：

- `ReplayStrategy.preload` 增载 `industry: {code: industry}`（join stock_basic）。
- 引擎每日循环：`unfreeze_t1 → 止损扫描 → 熔断判断 → 执行 pending（t1_open）/策略信号 → 记净值`。BUY 在熔断日跳过；BUY 前行业集中检查；止损在信号前。
- 峰值回撤：引擎内维护历史最高 total_value。
- 与 Go 同参跑一致性对照测试（沿用 Iteration 2 的模式）。

### 3.5 风险指标：turnover / cost

`backtest_result` 增两列（`backtest_result` + DTO + 前端）：

- `turnover`（年化单边换手）：区间累计买入成交金额 / 平均总资产 ×（252 / 交易日数）。数值如 `8.6`（8.6 倍/年）。
- `cost`（年化交易成本占比）：累计（佣金 + 印花税 + 滑点）/ 平均总资产 ×（252 / 交易日数）。数值如 `0.012`（1.2%/年）。

引擎 `_generate_report` 里从 `portfolio`（成交/成本累计）算，落 report → `run_and_save` 写库。前端类型 `turnover?` 已预留，点亮；`cost` 新增。

### 3.6 一致性对照（Iteration 2 模式延续）

Python 回测与 Go 实盘对**止损/熔断/行业集中/max_position_pct** 同参数同输入 → 同一持仓演化断言（扩展 `backend/internal/service/trading_consistency_test.go` 与 `quant-engine/tests/test_broker_consistency.py`）。
