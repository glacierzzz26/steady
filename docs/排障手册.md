# Steady 排障手册（运维不慌版）

> 给**不懂代码**的系统主人：出问题先照这个走，不用看懂程序也能定位、能处理。
> 配套工具：`./scripts/health-report.sh` 一键体检；`docs/系统手册.md` 是「页面+代码说明书」。
> 适用环境：生产 VM（`ssh quant@192.168.0.201` 进发布目录）与本地开发环境通用。

---

## 0. 排障总流程（四步）

1. **跑体检**：在发布目录执行 `./scripts/health-report.sh` —— 一条命令打印 8 节（容器/DB/失败任务/数据新鲜度/因子信号净值/数据质量/磁盘备份/schema 漂移），末尾汇总异常项，还带非零退出码。
2. **看飞书**：收到过红卡没？「任务未执行」「执行失败」「数据健康检查」卡上都写明是哪个任务。
3. **看 Ops 页**：浏览器打开 `/ops` → 任务时间线看当日每个任务是否 success；服务状态卡看 6 个容器；数据健康检查卡看 7 项。
4. **按下方症状表处置**：找到对应症状照做；处置完重跑 `health-report.sh` 确认转绿。

> 先确认「今天是什么情况」：**非交易日**（周六日/节假日）没有采集与信号，一切停在上一交易日是**正常**的，不是故障。

---

## 1. 症状目录（症状 → 定位 → 处置）

### A. 页面数据停在昨天 / 某一天

- **定位**：Ops 页任务时间线里，当日「数据采集 → 因子 → 信号」链路上哪个任务不是 success；或跑体检看第 4 节「数据新鲜度」哪张表落后。
- **处置**：按 §3 速查表**手动补跑**对应环节（通常从最先失败的开始，链路是上游先修）。
  - 行情没到 → `sync-daily`；估值没到 → `sync-valuation`；因子没到 → `factors --date`；信号没到 → `signals --date`。
  - 补跑完的因子/信号会覆盖当日旧值（幂等），不会重复。

### B. 飞书一整天没消息

- **定位**：
  1. 打开页面「设置」→ 飞书配置：`enabled` 是否开启、webhook 是否填写正确（app_config 表，以库为准，不读环境变量）。
  2. 手动发一条测试卡：`docker exec quant-engine python -m app.cli notify --test` —— 能收到说明配置与网络正常。
- **处置**：配置关闭/错误 → 设置页改好保存；配置没问题但没卡 → 看 quant-engine 是否在跑（重启见 §4），或某个具体事件被源任务拖住（见 C/D）。

### C. 收到「⚠️ Steady · 任务未执行」红卡（该做没做）

- **含义**：某个通知事件的源任务，过了计划发送时间 **30 分钟**仍没有当日执行记录。卡片会写明源任务名。
- **源任务对应表**：

| 红卡事件 | 缺的源任务 |
|---|---|
| 策略信号 | `generate_signals`（19:30） |
| 自动交易 | `auto_trade`（19:35） |
| 净值快照 | `nav_snapshot`（21:05） |
| 每日汇总 | `daily_report`（21:00） |
| 数据质量 | `data_quality`（18:30） |
| 早盘简报 | `morning_brief`（09:10） |

- **处置**：按 §3 补跑对应源任务 → 下一分钟通知调度 tick 会重新检查，跑了就不再告警。
  - 若补跑仍失败，看失败原因（D）。

### D. 收到「❌ Steady · 执行失败」红卡

- **定位**：Ops 页「告警记录」或体检第 3 节看失败任务的 `message`（失败原因）。常见：数据源临时不可用、网络波动、上游数据没到。
- **处置**：按 §3 补跑该任务；**多数时候重跑一次即成功**。连续失败多次再考虑数据源层面（看日志 `docker logs --tail 200 <容器>`）。

### E. 收到「数据健康检查」异常卡（7 项逐项处置）

每天 18:30 检查 7 项，卡片上哪项标红修哪项：

| 检查项 | 含义 | 处置 |
|---|---|---|
| `coverage` 行情覆盖 | 池内股票有行情的占比 <90% | `sync-daily` 补行情 |
| `missing_days` 缺失交易日 | 近 10 个开市日有缺口 | `sync-daily --start <缺口起始日>` 补 |
| `duplicates` 重复数据 | 4 张表有重复行 | 先 `sync-*` 重跑观察；仍重复需人工查重（§5 查询） |
| `price_anomalies` 价格异常 | 单日涨跌幅超板块涨跌停上限 | 看卡片明细里的个股 code，核实该股当日是否异常/数据错 |
| `valuation` 估值同步 | 估值滞后 ≥3 天 | `sync-valuation` |
| `financial` 财务覆盖 | 财务陈旧/覆盖 <90% | `sync-finance --quarters 4` |
| `benchmark` 指数基准 | 沪深300 滞后 | `sync-index` |

### F. 某页面空白 / 接口报错

- **定位**：体检第 1 节看 `quant-backend` 是否 running；看后端日志 `docker logs --tail 200 quant-backend` 有无 `ERROR`/`panic`。
- **处置**：重启 backend（§4）。若 nginx 也挂了，页面连 CSS/路由都不正常，一并重启。

### G. 模拟交易没成交 / 持仓不对

- **定位**：Ops 时间线看 19:35 `auto_trade`、21:05 `nav_snapshot` 是否 success；失败原因看 task_run message。
- **处置**：手动执行当日模拟交易（等价前端「手动执行」按钮）：
  ```bash
  curl -X POST http://127.0.0.1:8080/api/v1/trading/execute-day   # 幂等，可重跑
  ```
  注意：**停牌股/数据缺失的会跳过，涨跌停会拒单**，不一定是故障。

### H. 首页全部打不开

- **定位**：体检第 1 节容器状态 —— 六个容器里 nginx/frontend/backend 是否全 running；`curl -I http://127.0.0.1` 看响应。
- **处置**：进发布目录 `docker compose -f docker-compose.run.yml up -d`（一键拉起全部）；单挂的重启单个（§4）。

### I. 回测一直 running / pending

- **定位**：回测任务是 **DB 队列**，由 quant-engine 每 5 分钟消费。一直 pending → quant-engine 没在消费。`docker logs --tail 50 quant-engine` 看 `backtest` 相关日志。
- **处置**：重启 quant-engine（§4）。任务真失败看回测中心里该 job 的 `error`。

### J. 磁盘满 / 备份失败

- **定位**：体检第 7 节（根分区使用率 >90% 会标红；backup/ 最新备份是否当天）。
- **处置**：
  - 手动备份一次：`./scripts/backup-db.sh`（自动只保留 30 份）。
  - 磁盘紧张：`docker image prune -f` 清镜像缓存；`find backup -name '*.sql.gz' | xargs ls -S | tail` 看旧备份可手工删。
  - 备份目录为空 → 检查宿主机 cron：`crontab -l | grep backup`，缺失则补 `30 2 * * * <发布目录>/scripts/backup-db.sh`。

### K. schema 漂移（体检第 8 节标红）

- **含义**：`init.sql` 里定义的列，现库没有 —— 通常是版本升级没跑到迁移。
- **处置**：进发布目录 `./scripts/migrate.sh`（幂等，已应用的跳过）；开发改 schema 需遵守「同步更新 init.sql + 新增幂等迁移」两条规矩，详见 `deploy/README.md`。

## 3. 手动补跑速查表

容器 WORKDIR 均为 `/app`，直接 `docker exec` 即可（与定时任务同一套代码）。

| 环节 | 定时时间 | 手动补跑命令 |
|---|---|---|
| 股票列表/池 | 09:00 | `docker exec quant-collector python -m app.cli sync-stock` |
| 交易日历 | 09:05 | `docker exec quant-collector python -m app.cli sync-calendar` |
| 财务 | 18:00 | `docker exec quant-collector python -m app.cli sync-finance --quarters 4` |
| 当日行情 | 18:10 | `docker exec quant-collector python -m app.cli sync-daily` |
| 单只/区间行情 | — | `docker exec quant-collector python -m app.cli sync-daily --code 600519 [--start 20260801 --end 20260819]` |
| 指数行情 | 18:15 | `docker exec quant-collector python -m app.cli sync-index` |
| 当日估值 | 18:15 | `docker exec quant-collector python -m app.cli sync-valuation` |
| 指定估值 | — | `docker exec quant-collector python -m app.cli sync-valuation --codes 600519,000001` |
| 历史回填 | — | `docker exec quant-collector python -m app.cli backfill --start 20160801 --end 20260819 [--codes ... --dry-run]` |
| 估值回填 | — | `docker exec quant-collector python -m app.cli backfill-valuation` |
| **因子** | 19:00 | `docker exec quant-engine python -m app.cli factors --date 2026-08-21`（不带 --date 用最近行情日） |
| 因子检验预计算 | 19:05 | `docker exec quant-engine python -m app.cli factor-stats` |
| **策略信号** | 19:30 | `docker exec quant-engine python -m app.cli signals --date 2026-08-21` |
| 回测 | — | `docker exec quant-engine python -m app.cli backtest --start 2025-01-01 --end 2026-08-20 --top-n 20 --fill-mode t1_open --save` |
| 偏差报告 | — | `docker exec quant-engine python -m app.cli backtest-deviation` |
| **模拟交易** | 19:35 | `curl -X POST http://127.0.0.1:8080/api/v1/trading/execute-day`（幂等） |
| 净值/对账/LLM 解读 | — | 无手动命令：backend 任务**重启即自动补跑**到点没跑的 |
| 市场热点/早报/数据健康 | — | 无手动命令：次日定时自愈（数据健康重检） |

> 提示：`sync-daily` 不带参数按「股票池 ∪ 已有行情」全量走，日常补当天数据用它即可；只补一只用 `--code`。

## 4. 容器与日志操作

```bash
# 看六个容器状态
docker ps -a --format 'table {{.Names}}\t{{.Status}}' | grep quant-

# 重启单个容器（进发布目录，compose 文件名为 docker-compose.run.yml）
docker compose -f docker-compose.run.yml restart quant-backend
docker compose -f docker-compose.run.yml restart quant-engine
docker compose -f docker-compose.run.yml restart quant-collector

# 一键拉起全部（升级/回滚后也是这个）
docker compose -f docker-compose.run.yml up -d

# 看日志（最近 200 行，跟随）
docker logs -f --tail 200 quant-backend
docker logs --tail 200 quant-engine      # 因子/信号/回测/健康检查/通知调度
docker logs --tail 200 quant-collector   # 采集
docker logs --tail 200 quant-nginx       # 入口
```

> 本地开发环境用 `./scripts/dev-up.sh` 起全部（compose 文件名 docker-compose.yml）；生产是 `docker-compose.run.yml`。

## 5. DB 直查速查

```bash
Q() { docker exec quant-postgres psql -U quant -d quant_system -tA -c "$1"; }

# 某任务最近记录（含失败原因 message）
Q "SELECT run_date, status, message FROM task_run WHERE task_name='data_quality' ORDER BY run_date DESC LIMIT 5"

# 最近 3 天所有失败任务
Q "SELECT run_date, task_name, left(message,80) FROM task_run WHERE status='failed' AND run_date >= current_date-3"

# 各表最新日期
Q "SELECT 'daily_price', max(trade_date) FROM daily_price WHERE code NOT LIKE 'sh%'
   UNION ALL SELECT 'factor', max(trade_date) FROM factor_value
   UNION ALL SELECT 'signal', max(trade_date) FROM strategy_signal"

# 某日因子行数（约 = 6 因子 × 池股票数）
Q "SELECT count(*) FROM factor_value WHERE trade_date='2026-08-21'"

# 账户最新净值
Q "SELECT trade_date, nav, total_asset FROM account_nav ORDER BY trade_date DESC LIMIT 3"

# 重复行排查（例：daily_price 同日同股重复）
Q "SELECT code, trade_date, count(*) FROM daily_price GROUP BY code, trade_date HAVING count(*)>1 LIMIT 10"
```

## 6. 备份与恢复

```bash
# 手动备份（每天 02:30 cron 自动做，留 30 份）
./scripts/backup-db.sh

# 恢复（危险操作：会用备份覆盖当前库，恢复前确认 backup/ 里是最新想要的）
gunzip -c backup/quant_system_YYYYMMDD_HHMMSS.sql.gz | docker exec -i quant-postgres psql -U quant -d quant_system
```

> 数据全在命名卷 `steady_postgres_data`，升级/回滚不碰数据；回滚 = 进旧版本目录重跑 `./install.sh`。

## 附：何时该升级 / 发布（给主人的版本观）

- 日常改动在 `dev` 分支；**发布只走 `master`**：`git checkout master && git merge dev && git push` → 本地 `./scripts/build-release.sh` → scp 到 VM → 新目录跑 `./install.sh`。
- 升级后 schema 列漂移由 `install.sh` 自动跑 `migrate.sh` 补齐；手工可 `./scripts/migrate.sh --check` 体检漂移。
